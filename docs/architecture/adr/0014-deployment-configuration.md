# ADR 0014: Deployment configuration

## Status
Accepted

## Decisions
- **Infrastructure as code:** `render.yaml` defines the API, worker, scheduler, Key Value
  and Postgres. All in `frankfurt` (closest Render region to Kenya); datastores reachable on
  the private network only.
- **Sizing from measurements** (load-test results, section 6): gunicorn sync workers at
  2 x vCPU; database pool 2 per worker with no overflow, so connections are predictable
  (instances x workers x 2).
- **Scheduler as its own single-instance service:** embedding beat in the worker would
  duplicate scheduled jobs when the worker scales.
- **Key Value with `noeviction`:** it holds the Celery queue; eviction would lose jobs.
- **Secrets never in the repository:** generated by Render (`SECRET_KEY`,
  `PROXY_SHARED_SECRET`) or prompted once on the API and referenced by the other services.
- **Deploys gated on CI** (`checksPass`); migrations in the pre-deploy step, and schema
  changes must be backward compatible (expand/contract) so rollbacks need no downgrade.
- **Proxy trust:** `TRUSTED_PROXY_COUNT=2` (Vercel + Render edge), safe only because the proxy
  secret refuses requests that bypass Vercel; verified with a real request after launch.
- **Derived Redis databases:** the broker and rate limiter default to `REDIS_URL` with
  databases 1 and 2, because blueprints cannot build strings.

## Consequences
- Production cannot deliver email until a provider backend exists (launch blocker).
- Capacity figures come from a laptop; they must be re-measured on the deployed stack.
